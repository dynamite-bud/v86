# XWAH-9 Phase 4 design: worker-per-vCPU execution

Goal: `cpus: N` buys real host parallelism — each vCPU runs in its own WebWorker, all instances of the multimem module over ONE imported shared guest memory, and a parallel guest workload shows wall-clock speedup. Everything below builds on decisions already landed and verified in code on `feature/XWAH-9/integration`: the Phase 2 time-sliced scheduler (`main_loop_smp`, cpu.rs:3337; `pick_vcpu`, cpu.rs:3405; vcpu.rs contexts/latches; `AP_STARTUP_ENABLED` gate, vcpu.rs:113), the Phase 3 imported-guest-RAM architecture (gram.wasm accessors incl. `gram_atomic_*`, gen/generate_gram_wasm.js:222-241; memidx-parametrized atomic emitters, wasm_builder.rs:1139-1340, currently `#[allow(dead_code)]`; starter.js:301-352 instantiation flow), `PREFIX_LOCK` tracked in all three decode paths with zero readers (instructions.rs:2146, jit_instructions.rs:137, analysis.rs:90), and the Layer A measurements (mailbox median 5.5–6.7 µs, p99 ≲ 37 µs — docs/smp-thread-test-plan.md). Default artifacts and the time-sliced paths stay byte-identical/behavior-identical; everything here is opt-in behind `smp_workers` and the existing `guest-ram-import` cargo feature.

## 1. Execution topology — DECISION: symmetric (b), staged through (c)

**Target: (b) — ALL vCPUs in workers; the main thread is the device host + chipset + UI.** The main thread keeps a full V86 construction exactly as today (its own wasm instance, CPU.init, devices, io.js) but never runs guest code; its instance is the authoritative home of the shared chipset (PIC, IOAPIC — both Rust statics reached via `device_raise_irq`, cpu.rs:4678, and the Rust MMIO intercepts, memory.rs:91-284), fw_cfg/CMOS counts, and the save/restore assembly point.

Why not (a) (BSP on main, APs in workers):

- **Device-host responsiveness kills it.** Under (a) the main thread still executes BSP slices synchronously (`do_many_cycles_native` ≈ 100k instructions ≈ 0.3–1.5 ms). Every AP mailbox RPC issued during a BSP slice waits for the slice to end: the measured 6 µs median becomes a p99 of *slice length* — a 100–200× regression on the number the whole §3 device story is budgeted around. Servicing mailboxes from inside BSP env-import callbacks reintroduces exactly the reentrancy the phase is supposed to remove.
- **It does not remove the `device_raise_irq` reentrancy hazard** (DOM event → synchronous `call_interrupt_vector` mutating guest stack/EIP outside `main_loop`) for the BSP — the one vCPU that takes nearly all device interrupts.
- **The profiling insight says (b) costs boot little.** Boot is interpreter/dispatch-heavy and device-serialized (docs/jit-profile-2026-08.md headline via phase-3 §Stage 6: 68 MIPS interpreter, cross-page exit churn; steady state ~1.1 % interpreted). Moving the BSP into a worker does not slow interpretation; it adds mailbox cost only to actual device accesses, which are serialized on the main thread either way. Boot was never the Phase 4 win; parallel steady-state workloads are, and there the BSP is symmetric with the APs.
- **Input latency improves under (b):** the device host is always inside its `Atomics.waitAsync` service loop, so a keyboard IRQ becomes doorbell-post + worker wake (µs), instead of waiting for a slice boundary or racing reentrantly.

**(c) — all vCPUs in ONE worker, time-sliced there — ships first (Stage W2).** It runs the *existing, landed* `main_loop_smp` unchanged inside a worker, over the imported shared memory, with devices on main. It needs the full mailbox, doorbell, worker clock, worker-side `codegen_finalize`, and `device_raise_irq` decoupling — i.e. all of (b)'s host plumbing — but zero new guest-visible semantics: still single-threaded execution, so no LOCK atomics, no IPI wire, no LAPIC split are needed yet. Every line of (c) is kept by (b); (a) would build a throwaway asymmetric device path. Incrementality verdict: (c) before (b), (a) never.

Both non-worker paths remain: `smp_workers` off → today's `main_loop`/`main_loop_smp` (cpu.rs:3274/3337) exactly as landed. Coexistence is clean because worker mode is selected purely by which JS drives the instance and one new export (§3); the Rust scheduler code is untouched.

## 2. The control region (shared, wasm-addressable)

All cross-thread state lives **inside the imported guest memory, above guest RAM**, so Rust reaches it through the existing gram accessor layer (no new import surface), JIT modules could reach it via memidx 1, and JS reaches it as `Int32Array` views over the same SAB — `Atomics.wait/notify` on views over a shared `WebAssembly.Memory` buffer is exactly what Layer A already exercises. The guest can never touch it: addresses ≥ `memory_size` are mmap-routed to the unmapped handler (io.js:40-56).

Layout (starter.js today sizes the memory at `memory_size + 1 page`, JIT scratch at `[memory_size, memory_size+0x2000)` — memory.rs `gram_jit_scratch_base`; Phase 4 adds `CTL_PAGES = ceil(ctl_size(N)/64K)` pages after it):

```
CTL_BASE = memory_size + 0x10000  (next page boundary after the scratch page)
per vCPU i (64-byte-aligned blocks to avoid false sharing):
  doorbell[i]        u32   — version counter; Atomics.add + notify on every post
  run_state_pub[i]   u32   — Runnable/WaitForSipi/Parked/Halted, published by the worker
  command[i]         u32   — RUN / PARK_REQ / PARKED_ACK / TERMINATE (quiesce protocol, §8)
  pending_irr[i]     8×u32 — fixed-interrupt vector bitmap (gram_atomic_rmw_or_32 to post)
  pending_tmr[i]     8×u32 — level-trigger bitmap, same protocol
  ipi_special[i]     u32   — INIT latch bit | SIPI latch bit | SIPI vector byte | NMI bit (atomic or/xchg)
  eoi_ring[i]        head/tail + 16×u32 — worker→main level-EOI notifications (SPSC)
  mailbox[i]         64 B  — the §6 RPC record, byte-for-byte the tests/threads/mailbox-protocol.js layout
routing_table:       N × {apic_id, ldr, dfr, tpr, enabled, runnable} u32 each + version
machine:             tsc_offset u64, buslock cell u32, jit_dirty ring (head/tail + 64×u32 phys pages)
```

A vector bitmap instead of an IPI ring is deliberate: posting is one atomic OR (idempotent, coalescing exactly like a real IRR — irr-already-set is already a drop today, apic.rs:889-893), so there is **no overflow case and no MPSC ring protocol** for the hot path. Only INIT/SIPI/NMI, which carry payload/edge semantics, use the latch word (mirroring the vcpu.rs latch design, vcpu.rs:77-79).

gram.wasm additions (generator + both variants, ABI comments per the Layer A signed-return note): `gram_atomic_load_32`, `gram_atomic_store_32`, `gram_atomic_rmw_cmpxchg_64`, `gram_notify(addr, count)`, `gram_wait32(addr, expected, timeout_ns)` (wasm `memory.atomic.wait32` — legal in workers, traps on the main thread, which we never do).

## 3. Per-worker main loop, scheduling, hlt

New export `set_worker_vcpu(index, total)` puts the instance in worker mode: `set_smp_cpus(total)` still runs (CPUID leaf 1/0xB, `get_firmware_cpus`, APIC ID = index<<24 — the phase-2 identity plumbing is reused verbatim), but a `WORKER_VCPU: Option<usize>` static makes `main_loop` take a third path:

```
main_loop() → if worker_mode { main_loop_worker() }
              else if vcpu::count() > 1 { main_loop_smp() }   // unchanged fallback
              else { today's fast path }                       // unchanged
```

`main_loop_worker` per iteration: (1) drain jit_dirty ring → `jit_dirty_page` locally; (2) consume `ipi_special` (INIT resets the live block via `reset_vcpu_block` — no `switch_to`, this instance owns exactly one vCPU, the swap/rotation machinery of vcpu.rs is simply never engaged; SIPI applies CS:IP to the *live* block); (3) merge `pending_irr/tmr` into the local LAPIC's irr/tmr (`gram_atomic_rmw_xchg_32` each word with 0); (4) `handle_irqs` — APIC leg only, unless index 0, which first issues the PIC-ack RPC when the PIC doorbell bit was set (§4); (5) `do_many_cycles_native`; (6) return the local `apic_timer(now)` deadline when halted. No rotation, no block swap, no TLB flush on any boundary — the phase-2 2–10 % switch tax disappears in worker mode.

**hlt parks in the worker JS loop** (keeping Rust's contract identical to today: `main_loop` returns an idle deadline): `instr_F4` in worker mode just sets `in_hlt` (IF=1) or publishes `run_state_pub = Parked` (IF=0 — today's `RunState::Parked` branch, instructions.rs:2191-2197); the worker loop then does `Atomics.wait(doorbell[i], seen, t)` with `t` = LAPIC-timer deadline for halted-IF=1, infinite for Parked/WaitForSipi. Wake = any doorbell post; re-entering `main_loop_worker` re-derives everything from the queues, so spurious wakes are harmless — the phase-2 invariant carries over.

**Wake-path map (today → worker doorbell equivalent):**

| Today | Site | Worker equivalent |
| --- | --- | --- |
| `apic::deliver` fixed IPI to non-current vCPU: `note_interrupt` + `stop_idling` | apic.rs:882-886 | sender: `gram_atomic_rmw_or_32(pending_irr[target])` + doorbell add + `gram_notify` |
| INIT/SIPI latches consumed at slice boundary | apic.rs:792-869 → cpu.rs:3439 | `ipi_special[target]` atomic-or + doorbell; consumed at worker loop step (2) |

| `device_raise_irq` → sync `handle_irqs` | cpu.rs:4678-4685 | main thread: pic/ioapic `set_irq` on the chipset instance → route → pending bitmaps + doorbells (never touches vCPU state — the reentrancy hazard is gone) |
| PIT/RTC/ACPI timer interrupts via `run_hardware_timers` in `main_loop` | cpu.rs:3304 | stay on main: a `setTimeout`/tick loop on the device host fires them through the same `device_raise_irq` path |
| LAPIC timer deadline returned to JS | apic.rs:617, cpu.js:2293 | worker-local: `Atomics.wait` timeout from its own `apic_timer` |

## 4. Interrupt delivery

**Authoritative LAPIC home: the vCPU's own worker instance** (`APICS[local]`). A shared-memory APIC block is rejected: `acknowledge_irq` runs on the hot interrupt path inside the instance, the `Apic` struct layout is a private-memory `repr(C)` contract with save/restore (cpu.js:709), and sharing it would reintroduce cross-instance locking on every instruction boundary — against the whole option-A architecture. What *is* shared is the minimum the senders need: the routing snapshot.

- **Routing snapshot:** each worker publishes `apic_id, LDR, DFR, TPR, enabled` on change (`write_routing_register` apic.rs:393-411 gains a publish call; TPR writes likewise). Senders (worker ICR writes, main IOAPIC) resolve destination matching (`lapic_matches_destination` logic, apic.rs:763-788) and lowest-priority arbitration against the snapshot. Staleness races are exactly the races real hardware has; lowest-priority already uses TPR-not-PPR (documented, multicore.md:286) and now uses `runnable` from `run_state_pub`.
- **ICR sends** (`write_icr0`, apic.rs:433+, executing inside the sending worker since LAPIC MMIO is Rust-intercepted, memory.rs:280): self-targets deliver locally as today; remote targets post to `pending_irr`/`ipi_special` + doorbell. Shorthands fan out over the snapshot. `route()` grows a worker-mode leg; the time-sliced leg is untouched.
- **IOAPIC stays on the main thread's chipset instance.** `ioapic::set_irq → check_irq → apic::route` (ioapic.rs:113-168) runs there; in worker mode `deliver` becomes the bitmap post. "Delivered" (the remote-IRR contract, ioapic.rs:136) = a snapshot match was found — sound because a worker LAPIC always accepts a fixed vector into irr (already-set coalesces, same as today). **Level EOI** (`write_eoi` tmr leg, apic.rs:416-431) cannot call `ioapic::remote_eoi` from a worker: it posts the vector on `eoi_ring[i]` + a main-side doorbell; the device host drains the rings in its service loop and calls `remote_eoi` on the chipset instance. IOAPIC MMIO (0xFEC00000) from a worker is forwarded to main as an ordinary mmap RPC (worker-mode special case at memory.rs:94/137/284); it is cold (setup-time).
- **8259/ExtINT stays wired to vCPU 0** (handle_irqs gate, cpu.rs:4637): PIC INTR assertion on main posts a PIC flag + doorbell[0]; the BSP worker's `handle_irqs` then performs one mailbox RPC `pic_acknowledge` (main runs `pic::pic_acknowledge_irq()` on the chipset instance, returns the vector) and calls `pic_call_irq` locally. One 6 µs RPC per 8259 interrupt; ACPI-mode Linux takes almost everything through the IOAPIC path, which needs no RPC.

Consumption timing: workers consume at every `main_loop_worker` iteration (≈ per 100k-instruction slice) and on every park wake — the same boundary the time-sliced scheduler uses today, so no new interrupt-latency class is introduced.

## 5. LOCK → atomics

All gated on the `guest-ram-import` feature (plus runtime "shared" flag), keeping the default artifact byte-identical by construction, same discipline as Phase 3 Stage 1/4.

**The LOCKable set and where each lands** (all `_mem` forms; `_reg` forms with LOCK must `#UD` — fixing today's silent discard, instructions.rs:2140-2146):

| Instructions | Today's path | Atomic lowering |
| --- | --- | --- |
| ADD/OR/ADC/SBB/AND/SUB/XOR (00-31, 80/81/83 groups), NOT/NEG (F6-F7/2-3), INC/DEC (FE-FF/0-1), XADD (0FC0/C1), CMPXCHG (0FB0/B1) | `safe_read_write{8,16,32}` closures (cpu.rs:4112-4185, instructions.rs, instructions_0f.rs:3619-3811) | generic CAS loop in `safe_read_write*`: when `*prefixes & PREFIX_LOCK` (or implicit) and phys is aligned + non-mmap + non-page-crossing → `loop { old = gram_atomic_load; new = closure(old); gram_atomic_rmw_cmpxchg(old,new) == old → break }`. Closure re-execution is idempotent (recomputes flags from the new `old`). Aligned add/sub/and/or/xor/xchg MAY later specialize to single RMW (old = rmw_op; run closure for flags only) — optimization, not required for correctness |
| XCHG mem (86/87) | same closures (instructions.rs:827-832) | **implicitly locked**: same path, LOCK behavior forced for mem forms |
| BTS/BTR/BTC mem (0FAB/B3/BB, 0FBA/5-7) | byte-level translate+read8+write8 (arith.rs:1024-1047) | single-byte ⇒ always aligned: `gram_atomic_rmw_{or,and,xor}_8`, flags from returned old value |
| CMPXCHG8B (0FC7/1) | bespoke read64/write64 (instructions_0f.rs:3972-3993) | new `gram_atomic_rmw_cmpxchg_64` when 8-aligned; else bus lock |

**Misaligned / page-crossing / mmap-target locked accesses — the bus lock.** gram atomics trap on unnatural alignment (documented in the gram ABI, generate_gram_wasm.js:33-36). Fallback hierarchy: (i) *interim* (Stage L1): global mutex cell in the control region — CAS-acquire via `gram_atomic_rmw_cmpxchg_32`, plain RMW (the existing `virt_boundary_*` machinery), fence, release. Documented hole: an *aligned* atomic on an overlapping cell ignores the bus lock — guests that mix aligned atomics with misaligned-locked overlapping accesses are architecturally deranged and modern kernels trap split locks themselves. (ii) *final* (after Stage W4 lands quiesce): exclusive execution — request PARK of all other workers, perform the RMW, resume; this is precisely QEMU MTTCG's `start_exclusive` and makes bus-lock semantics exact. Profiler-counted either way. MMIO-target LOCK just takes the normal mmap RPC (device access is main-thread-serialized anyway).

**L1 implementation note (landed).** The interim bus-lock cell is **instance-local** (a static `AtomicU32` in cpu/lock.rs), not yet in the control region: the control region does not exist until W1, and in L1 no second instance of the module exists — JS-side contenders race via aligned gram atomics on guest cells, which by design ignore the bus lock (the split-lock hole above). W1 relocates the cell to `machine.buslock`; the CAS-acquire/fence/release protocol is already the cross-instance one. Fence resolution: the main module is built without the wasm atomics target feature, where `core::sync::atomic::fence` lowers to nothing (LLVM drops singlethread fences), so the bus-lock sections bracket the plain RMW with gram.wasm's exported `gram_fence` (a real seq-cst `atomic.fence`). Locked `_reg` forms `#UD` from the generated interpreter dispatch (`lock: 1` table flag → `crate::ud_if_lock_prefix!` guard), not from the hand-written `_reg` bodies: the guard must not perturb the default artifact, whose byte-identity extends to the panic-Location line numbers embedded in the data section — generated files are the one place a line-neutral, order-neutral splice exists for all 96 forms.

**Page-table A/D bits** (`do_page_walk` writes, cpu.rs:2129-2131/2181-2189): replace the read-entry/`memory::write8`-low-byte pattern with a `gram_atomic_rmw_cmpxchg_32` loop on the entry's low dword that rechecks PRESENT before setting A/D and retries on change — the SDM's locked-walker semantics, and the QEMU MTTCG precedent. (Plain-byte OR would be atomic but could set A on a just-cleared PTE.)

**JIT emission** (Stage L2): the single choke point is `gen_safe_read_write` (codegen.rs:1006) — every LOCKable table entry already funnels through it via jit_instructions.rs, so **no instruction-table changes**. When `ctx.cpu.prefixes & PREFIX_LOCK` (set at jit_instructions.rs:137; forced for 86/87 mem): fast path adds an alignment test to the existing TLB-hit condition and wraps the already-emitted closure in a wasm CAS loop using the Stage-2 emitters (`atomic_rmw_cmpxchg_*`, memidx `GUEST_MEMORY_INDEX`, wasm_builder.rs:1314-1340 — their first live callers); the slow path must NOT take the scratch-page redirection (`safe_read_write*_slow_jit`, cpu.rs:3843-3855, is non-atomic by design) — it calls a new `safe_read_write*_locked_slow` helper that shares the interpreter's CAS/bus-lock code. bt-family and cmpxchg8b are `custom: 0` interpreter calls from JIT'd code already, so they inherit L1.

**Memory ordering.** Locked ops: wasm atomics are seq-cst, strictly stronger than x86's locked semantics — done, no decision needed. **Plain guest accesses: take the MTTCG-style calculated default risk; no fences by default; escape hatch `smp_memory_model: "relaxed" (default) | "fenced"`.** Rationale: on x86 hosts, V8 lowers plain wasm loads/stores to plain x86 loads/stores, so host TSO gives guest TSO essentially for free — the risk window is weakly-ordered hosts (Apple Silicon, ARM servers). Cost of closing it: fencing means seq-cst-izing (or `atomic.fence`-bracketing) guest stores in `gen_safe_write`/gram — an mfence-class operation (~10 ns) per store on x86, dmb-class on ARM; at ~1 store per 3 instructions and JIT throughput in the hundreds of MIPS that is order **+30 % on every workload** (same estimation method as spike S2's gate math), paid even by single-threaded guests under `cpus > 1`. Against that: Linux's own synchronization is LOCK/xchg-based (which we make seq-cst), and the exposure is unfenced store→store / load→load reordering visible only to racing plain accesses — the TSO litmus tests (test-plan Layer C item 6, MP + SB histograms) are the detector and the decider, run on ARM in CI-adjacent tooling. The escape hatch is a runtime flag consumed by `gen_safe_write`/gram selection — files we own end to end (the Addendum 2 property). Device-side ring publications get their own cheap rule in §6 regardless.

New `src/browser/vcpu_worker.js`: receives `{wasm_source, gram_bytes, guest_memory, index, total, main_time_origin, memory_size}`, instantiates gram + main module (the `build_env` shape from starter.js:307-352 factored to be reusable), calls `rust_init`, `set_smp_cpus`, `set_worker_vcpu`, `set_guest_memory_shared(1)`, then runs the park/slice loop. No io.js, no devices, no CPU.js facade in the worker.

**Cross-worker JIT dirty-page shootdown:** a worker's own writes invalidate its own cache synchronously (unchanged, `jit_dirty_page`). For *other* instances, every `jit_dirty_page` call additionally posts the phys page to the machine jit_dirty ring + doorbells all workers; consumers drain it as loop step (1), **before** IPI/IRR consumption — x86 requires a serializing operation (typically the cross-modifying-code IPI handshake) before executing modified code, so draining dirt before delivering interrupts preserves the architectural contract at slice granularity. Guest TLB shootdown needs nothing beyond IPI delivery: each instance's TLB is private and the target executes its own INVLPG in its handler.

**Virtio/DMA zero-copy:** rings and payloads stay direct main-thread views over the SAB (phase-3 §3 property, S4 audit). Synchronization: guest→device is ordered by the notify-port mailbox RPC (the seq-cst STATE store publishes all prior plain ring writes — the shared-view-coherence.js rule); device→guest interrupt-driven consumption is ordered by the IRQ doorbell post. The one uncovered edge is a *polling* guest (event-idx/NO_NOTIFY suppression) reading used-ring updates with plain loads: rule — **device-side ring index/flag publications use `Atomics.store` on the SAB view** (a handful per batch, negligible), so element-before-idx ordering holds even against relaxed guest reads; guest-side reads then fall under the §5 ordering decision. Same rule applies to `dma.js`/`ide.js` completion flags (their bulk `.set()` payloads stay plain, ordered by the subsequent IRQ doorbell).

Residual hot RPCs stay as predicted (phase-3 §3): legacy VGA 0xA0000 and IDE PIO data. At 6 µs/access a text-mode scroll (~2k word writes) costs ~12 ms — acceptable, listed as a known cost; mitigation if needed is a batched string-op fast path, out of scope.

## 7. Save/restore across workers (Phase 5 tail, protocol fixed now)

- **Quiescence:** main sets `command[i] = PARK_REQ` + doorbell for every worker; workers ack `PARKED_ACK` at the next slice boundary (bounded by one slice, ms-scale). The device host **keeps servicing mailboxes while waiting** — a worker mid-RPC completes the RPC and parks at its next boundary; no deadlock. Parked means: not in `do_many_cycles`, mailbox IDLE, doorbell waited.
- **State assembly:** on request, each parked worker runs `vcpu_prepare_save` (vcpu.rs:303) and posts its 1216-byte save area + latch bytes (the exact `Vcpu` repr(C) layout, vcpu.rs:69-88) and its `Apic` struct via postMessage. Main writes these bytes into *its own instance's* `VCPUS[i]`/`APICS[i]` regions (`get_vcpu_state_addr`, `get_apic_addr` — same module bytes ⇒ identical layout), then runs today's `get_state` unchanged. **The v7 format extends untouched**: slot 93 (`[u32 smp_cpus][u32 current]` + N×Vcpu, cpu.js:639-720) and the N-struct APIC blob are raw regions indifferent to which thread executed the vCPUs. `current` is written as the BSP.
- **Restore:** main validates and restores its instance exactly as today (fail-fast block intact), then spawns/resets workers and sends each its Vcpu block + APIC struct; the worker loads the block into its live area (`load_block` semantics with shared-field fixups), installs the APIC context, publishes its run state, and enters the loop. Cross-`cpus`/version rejection semantics are inherited verbatim (multicore.md §State images).
- `stop`/`destroy`: quiesce then `TERMINATE`; `restart`: quiesce, main-side `reset_cpu` for the chipset, per-worker reset commands (APs → WaitForSipi).

## 8. Failure modes, options, browser matrix

**Option surface:** `smp_workers: false (default) | true | "auto"`. `true` = hard requirement — synchronous constructor throw naming the missing capability (mirrors the multimem probe's loud throw, starter.js:118-127); requires `cpus ≥ 1`, `acpi: true` for cpus>1 (existing clamp, starter.js:450-461), and forces `guest_memory_backend: "imported"`, `guest_memory_shared: true`. `"auto"` = degrade down the ladder with a `dbg_log`. Ladder, top to bottom, each step observable:

1. **workers** — needs `crossOriginIsolated`/SAB, multi-memory (existing probe), `Worker`, successful spawn+instantiate of all N workers *before boot*;
2. **time-sliced over imported memory** (shared or not) — today's landed `cpus: N` + backend;
3. **time-sliced over linear memory** — today's default `cpus: N`.

Embedder observability: a `"smp-mode"` bus event at init-complete plus a stable `emulator.smp_mode` property `{execution: "workers"|"time-sliced", cpus_effective, guest_memory: {backend, shared}}` — extending multicore.md's contract table, which already concluded no public API needs a signature break; the three flagged semantic shifts (racy `read_memory`, approximate `get_instruction_counter` via per-worker counters summed from published cells, decoupled event timing) become real in worker mode and the doc rows flip from "outlook" to "current".

**Failures after boot are fail-stop:** worker `error`/`exit` → park remaining workers, emit `"emulator-error"` with the Error, stop the machine (a guest cannot survive losing a CPU; silent degradation mid-run would corrupt guest state). Spawn-time failures degrade cleanly (pre-boot, ladder step down). Shared-memory allocation failure throws synchronously at construction (allocation already happens there, starter.js:163-168).

**Browser gates:** Chrome is verified (S1 matrix, Chrome 151, incl. shared memidx-1 atomics and the main-thread `Atomics.wait` throw — which this design never violates: only workers block). Firefox and Safari cells of the S1/S3/S4 matrix remain the launch gates for those browsers (probe.html run, COI-served); Safari multi-memory is already the imported-backend gate and therefore transitively gates workers. Worker mode ships Chrome-first behind `"auto"` degradation; no new engine capability beyond Phase 3's list is required except `Atomics.wait` in workers (universally shipped) and `memory.atomic.notify/wait32` (part of the same threads proposal S1 already probes — add one probe.html cell).

## 9. Stages

LOCK stages (L*) are worker-independent and valuable alone: they give the multimem build real atomic semantics that a main-thread JS contender can already race against, and fix LOCK-on-register `#UD` fidelity. Worker stages (W*) build the host topology. Layer C tests (test plan items 1–7) land with the stage that makes them runnable.

- **L1 — interpreter LOCK + gram additions.** `PREFIX_LOCK` readers in `safe_read_write{8,16,32}`, bt-family, cmpxchg8b, implicit XCHG; CAS-loop + interim bus-lock cell; A/D cmpxchg walker; `#UD` for locked register forms; gram gains atomic load/store/cmpxchg_64/notify/wait32. Gated on `guest-ram-import` (default artifact byte-identical; expect goldens untouched). Gates: nasm/qemu differential green on the multimem variant; new `tests/threads/` guest-vs-JS-thread exactness test (guest `lock inc` under one vCPU vs main-thread `Atomics.add`, exact total — Layer C item 1's substrate, runnable *now* on the Layer B harness); default suites byte-identical.
- **L2 — JIT LOCK (landed).** `gen_safe_read_write` CAS-loop fast path (first live use of the wasm_builder Stage-2 atomic emitters), `locked_slow` helpers replacing scratch redirection under LOCK. Gates: multimem expect goldens (new, variant-only), DISABLE_JIT=0 differential runs, Layer C item 1 exact under JIT.
  **L2 implementation note (landed).** The single seam is a line-neutral `jit_locked_read_write!` macro at the top of `gen_safe_read_write` (codegen.rs) diverting to `codegen::locked::gen_safe_read_write_locked` (codegen_locked.rs) when `ctx.cpu.prefixes & PREFIX_LOCK` — set at jit_instructions.rs:137, and forced for XCHG mem 86/87 by the pass-through `jit_locked_xchg_read_write!` wrapper at those three call sites. Fast path: the TLB-hit condition additionally requires natural alignment, then a seq-cst CAS loop over memidx 1 (plain first load validated by `atomic_rmw_cmpxchg_{u8,u16,i32,i64}`; the i64 emitter is new for CMPXCHG8B). Closures emit register/flag side effects while computing the value, so the loop snapshots the 8 register locals + the five lazy-flag globals into wasm locals and restores them on every retry — the wasm-level mirror of L1's `LockRetrySnapshot`, making the surviving side effects exactly the successful iteration's. Slow path: `safe_read_write{8,16,32s,64}_locked_slow_jit` (cpu/lock.rs) — a pure TLB fill on an aligned non-mmap target returns the real tag (bit 1 clear) and the emitted CAS loop provides atomicity; page-crossing/mmap/misaligned classes acquire the L1 bus lock, redirect to scratch, and return tag|2, whereupon the emitted code runs the closure against scratch and `safe_write{8,16,32,64}_locked_slow_jit` performs the real write and releases the lock (same split-lock hole as L1). Table-claim correction: bt-family mem forms are NOT interpreter calls — they are `custom: 1` and funnel through `gen_safe_read_write` BYTE via `gen_bit_rmw` (jit_instructions.rs:2104), so they inherit the L2 byte CAS; likewise CMPXCHG8B (0FC7/1, `custom: 1`) is JIT-inlined as the one QWORD user. Only CMPXCHG r/m8 (0FB0) and XADD r/m8 (0FC0) are non-custom interpreter calls, and they do NOT inherit L1 for free: the runtime `prefixes` global is always 0 during compiled execution (the JIT consumes prefix bytes at compile time), so the generated dispatch's call would reach `safe_read_write8` without the LOCK bit. generate_jit.js therefore splices the line-neutral `jit_lock_interp_mem_call!` wrapper (codegen.rs) around exactly these two mem calls: for a LOCK-decoded instruction it brackets the interpreter call with emitted stores materializing the compile-time prefixes into the runtime global and clearing them after (straight-line, so the clear also runs on the page-fault return path), routing the body into L1's byte CAS/bus lock. Known remaining fidelity gap (pre-existing, unchanged by L2): locked `_reg` forms #UD only from the interpreter dispatch — compiled code still silently discards LOCK on register forms. Variant-only expect goldens are deferred: tests/expect has no multi-build discovery (one golden per .asm, default artifact only, hook asserted to fire exactly once — run.js:27-41/101-105); coverage comes from the JIT-warmed exactness phases (tests/threads/guest-lock-exactness.js: inc/xadd/xadd8/cmpxchg8b + page-crossing, force-compiled via `jit_force_generate_unsafe` with generation-tracked finalize evidence (recompiles with grown entry-point sets are expected; the final generation must survive)) and the engine-executed emitter dump (`multimem_builder_test` + tests/rust/verify-wasmgen-multimem-output.js).
- **W1 — control region + worker runtime skeleton (landed).** starter.js sizing, control-region module in Rust (`smpctl` over gram), `vcpu_worker.js` instantiating module+gram over the shared memory in a real worker, clock origin handshake, mailbox wired to the worker's env (against a stub device host). Gates: extended multimem-instance.js proving instantiate+RPC+doorbell against the real module in `worker_threads`; mailbox latency within 2× of the Layer A baseline.
  **W1 implementation note (landed).** The layout (src/rust/cpu/smpctl.rs, authoritative; JS mirror src/browser/smpctl.js, equality asserted field-by-field through the `get_smpctl_base`/`get_smpctl_size`/`get_smpctl_offset` probe exports): per-vCPU stride 0x240 with each §2 field in its own 64-byte block (doorbell 0x000, run_state_pub 0x040, command 0x080, pending_irr 0x0C0, pending_tmr 0x100, ipi_special 0x140, eoi_ring 0x180, mailbox 0x200), then routing (version line + one 64-byte line per entry), then the machine block (0x1C0: tsc_offset 0x00, buslock 0x40, jit_dirty ring 0x80). **Benchmark acceptance (phase success bar, honest against device serialization and the ~6 µs mailbox):** on a 2-vCPU worker configuration, Apple-M-class host, Alpine SMP fixture: (1) a CPU-bound 2-thread workload with negligible I/O (`stress-ng --cpu 2` fixed-ops, or a two-thread checksum loop) completes in **≤ 0.67× the wall-clock of cpus=1 worker mode (≥ 1.5× speedup)** and **≥ 1.4× vs cpus=2 time-sliced**; (2) a mixed workload (`make -j2` of a small C tree in tmpfs) shows **≥ 1.15× vs time-sliced** (9p/device serialization bounds it); (3) single-threaded workload regression **≤ 10 %** vs time-sliced; (4) zero lost updates / soft-lockups across the Layer C suite. 4-vCPU numbers reported informatively, not gated.

## Risks

Mailbox p99 spikes under host load starving PIC-ack/PIO paths (mitigation: nothing latency-critical behind the mailbox — clock and LAPIC are local; measured baseline in the test plan); TSC sync-check flakiness at µs offsets (fallback clocksource is functional); plain-access reordering on ARM until W5 decides the fencing posture (litmus detector in place); interim bus-lock cell hole vs aligned racers (upgraded in W4, split locks pathological); jit-dirty ring overflow under pathological cross-modifying storms (drain-before-IRQ + sized ring, overflow → full local `jit_clear_all`); routing-snapshot staleness during IPI bursts (bounded by hardware-equivalent races); worker spawn/CSP variance across embedders (pre-boot degradation only); Safari remains the ladder's hard bottom until its multi-memory cell resolves.
