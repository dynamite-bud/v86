# XWAH-9 multi-threaded test plan (tests/threads)

Every pre-existing suite — expect goldens, nasm/qemu differential, OS boot,
api tests, jit-paging, kvm-unit-tests, and the Phase 2 SMP acceptance
(tests/api/smp.js, smp-state.js) — validates SINGLE-THREADED execution: the
time-sliced SMP work multiplexes vCPUs on one thread, and nothing tests
cross-thread semantics. Phase 3 (docs/smp-phase3-design.md) moves guest RAM
into a shareable `WebAssembly.Memory`; Phase 4 runs vCPUs in workers. This
plan layers every concurrency property by the earliest point it becomes
testable, and Layer A is implemented now in `tests/threads/`.

The Layer A harness shape is deliberately the Phase 4 shape: K
`worker_threads`, each with its OWN wasm instance (gram-shared.wasm, the
Stage 3 guest-RAM accessor module) imported over ONE shared guest memory,
synchronized with the same Atomics primitives Phase 4 will use (worker-side
blocking `Atomics.wait`, main-thread `Atomics.waitAsync` — spike S3).

## Layers

| Layer | Testable | Substrate | What it can prove |
| --- | --- | --- | --- |
| A | NOW | gram[-shared].wasm (Stage 3, generated on demand) + worker_threads + SAB | The primitives Phase 4 is built on: emitted wasm atomics are truly atomic cross-instance/cross-thread, plain accesses truly race, the §3 mailbox protocol works losslessly, shared views cohere under an Atomics handshake |
| B | Stage 4/5 merge (build/v86-multimem-debug.wasm + starter option) | full multimem module over imported shared guest RAM, one guest thread + JS-view workers | The real module keeps those properties: main-thread device views vs wasm-side guest RAM traffic on the same memory, while a guest actually executes |
| C | Phase 4 (worker vCPUs) | ≥2 vCPUs on real threads | End-to-end x86 semantics under true parallelism: LOCK, IPIs, TLB shootdown, TSO, guest workloads |

## Layer A — implemented now

All standalone Node ESM scripts (`node:assert/strict`, no framework, each
directly runnable; `run-all.js` drives the directory). gram-shared.wasm is
generated by the test itself when absent (`gen/generate_gram_wasm.js`), so
no build step is required. Measured numbers below: Node v24.18.0, Apple M4,
3 consecutive full-suite runs, zero flakes.

### tests/threads/atomics-exactness.js

- **Asserts**: 4 workers × 1e6 `gram_atomic_rmw_add_32` on one cell through
  4 separate gram instances over one shared memory sum to EXACTLY 4,000,000;
  mixed-width variant (add_8/add_16/add_32 on disjoint cells, 4×250k) exact
  per width with guard bytes adjacent to the 8-bit cell untouched; cmpxchg
  contention (4 workers CAS-looping to 100k successes each) lands exactly on
  400,000.
- **Why now**: needs only Stage 3's artifact; this is the load-bearing
  "emitted atomics are really atomic" proof and should gate Stage 4 codegen
  work, not follow it.
- **Failure caught**: an engine or emission bug (wrong opcode/memarg, wrong
  memidx, non-atomic lowering) that loses updates — which at Phase 4 becomes
  corrupt guest spinlocks/refcounts, the least debuggable failure mode SMP
  has.
- **Observed**: exact in every run; ~1.1 s per 4M-op phase; CAS retry rate
  ~0.86–0.95 retries/success at K=4 (real contention, healthy convergence).

### tests/threads/plain-race-vs-atomic.js

- **Asserts**: the same harness with PLAIN `gram_read32`/`gram_write32`
  read-inc-write must never exceed K*N, and across 5 attempts should lose
  updates at least once (observed: 42–65 % lost, 5/5 attempts, every run);
  then the atomic variant must be exact. If no attempt loses an update the
  test logs INCONCLUSIVE rather than failing (interleaving is
  timing-dependent; a pass-by-luck must not turn the suite red).
- **Why now**: methodology self-validation — proves the exactness assertions
  in atomics-exactness.js are signal, not luck, on this host.
- **Failure caught**: a harness that cannot detect lost updates (workers
  serialized, memory secretly not shared, iteration counts too low) would
  make every other Layer A pass meaningless.

### tests/threads/mailbox-protocol.js

- **Asserts**: executable reference implementation of the design §3 mailbox
  — 64-byte per-vCPU record `{state, op, addr, size, value_lo, value_hi}` on
  a control SAB; worker (vCPU role) does plain-field-write + seq-cst
  `Atomics.store(STATE)` + notify + blocking wait; main thread (device role)
  services via `Atomics.waitAsync`. 10,000 port-I/O RPCs (5,000 OUT+IN
  echo pairs): every request serviced exactly once, strictly in issue order,
  values intact both directions; round-trip latency reported.
- **Why now**: the protocol is pure JS + SAB; proving it lossless before
  Phase 4 means Phase 4 debugs vCPU code, not its transport. This file IS
  the Phase 4 protocol reference.
- **Failure caught**: lost wakeups (notify before wait, stale `waitAsync`
  re-arm races), field tearing (missing publication edge), out-of-order
  service.
- **Observed**: 0 lost wakeups over 30k RPCs (3 runs); round-trip median
  5.5–6.7 µs, mean 6.0–8.7 µs, p99 13.5–36.7 µs, max ≲ 390 µs.

### tests/threads/shared-view-coherence.js

- **Asserts**: worker writes through EVERY gram write export (8/16/32/64/128,
  memset, memcpy) → after an Atomics handshake the main thread sees all of
  it through plain `DataView`/`Uint8Array` views (the device-model pattern);
  reverse direction: 4 KiB of main-thread JS-view writes visible through
  gram read accessors after the handshake.
- **Why now / why the handshake is load-bearing**: plain writes to shared
  memory carry NO cross-thread visibility/ordering guarantee by themselves;
  only seq-cst atomics create happens-before edges, and weakly-ordered hosts
  (ARM Macs) can genuinely reorder plain stores. The test documents and
  enforces the rule Phase 4 devices live by: bulk payload stays plain and
  borrows visibility from an atomic doorbell. Deliberately NOT asserted:
  visibility without a handshake (it can pass by luck and would enshrine an
  anti-pattern).
- **Failure caught**: an accessor writing through a stale/private memory, a
  view over the wrong buffer, or a broken publication edge — at Phase 4,
  virtio rings whose descriptors devices half-see.

### tests/threads/run-all.js

Sequential driver over the directory (skips itself and helpers.js),
mirroring how the Makefile unit-test targets list their scripts; sequential
on purpose since each test saturates several cores and the race
demonstration wants an unloaded machine. Full suite ≈ 12 s.

## Layer B — written now, gated until Stage 4/5 merge

### tests/threads/multimem-instance.js

- **Gate**: `Missing build/v86-multimem-debug.wasm, test skipped` (repo
  pattern); additionally skips if starter.js lacks the Stage 5
  `guest_memory_backend` option, or if the created guest memory is not
  SAB-backed in Node.
- **Asserts (once live)**: boot SeaBIOS (no disk) with
  `guest_memory_backend: "imported"`; while the guest executes, a worker
  drives JS-view traffic on a disjoint 48 MiB-offset region of the SAME
  shared guest RAM — 1e6 `Atomics.add` increments must be exact despite the
  live guest, worker plain writes must be visible through the public
  `read_memory` API after join, `write_memory` must land in the shared
  buffer, and the guest must still be running.
- **Assumptions to finalize at merge** (stated in the file): A1
  `options.guest_memory_backend: "imported"` selects the multimem artifact;
  A2 guest RAM reachable as `emulator.v86.cpu.mem8.buffer` (SAB in Node);
  A3 `read_memory`/`write_memory` route through the imported memory; A4
  SeaBIOS POST does not touch 48 MiB in a 64 MiB machine.
- **Why not earlier**: needs the Stage 4 artifact (sibling branch, in
  flight) and Stage 5 JS integration.
- **Failure caught**: the full module regressing what gram.wasm proves in
  isolation — e.g. Rust-side accessor imports wired to a different memory
  than the JS views, or device APIs still reading a stale private copy.

## Layer C — Phase 4 (worker vCPUs); designed now so Phase 4 starts with a checklist

Each of these needs real guest code on ≥2 host threads and cannot run
earlier because today's SMP is time-sliced (a single thread cannot exhibit
lost updates, delivery races, or memory-ordering relaxation):

1. **LOCK atomicity** — two vCPUs hammer `lock inc dword [cell]` (and
   `lock cmpxchg` loops) on one guest cell; totals must be exact. Guest-level
   twin of atomics-exactness.js; catches the JIT's LOCK lowering (Stage 2
   atomic emitters, memidx 1) and the interpreter's `safe_read_write` RMW
   path disagreeing or silently degrading to plain RMW. Vehicle:
   kvm-unit-tests (in-repo; needs 32-bit gcc — CI follow-up from Phase 2
   Stage 4) or a flat binary poked into guest RAM.
2. **IPI / TLB-shootdown delivery under parallelism** — vCPU A munmaps/
   remaps while vCPU B faults through the same page; INVLPG+IPI storms must
   never let B read through a stale TLB entry, and cross-vCPU INIT/SIPI/
   fixed IPIs must be delivered exactly once. Catches wake-vs-run races the
   time-sliced scheduler can never produce.
3. **Mailbox I/O RPC under load** — all vCPUs issuing port I/O concurrently
   (per-vCPU records; contended device side), IRQ doorbells in flight;
   assert per-vCPU ordering and no lost wakeups; compare latency against the
   Layer A baseline above.
4. **hlt/wake races** — vCPU parks in hlt exactly as an IPI/IRQ arrives;
   repeat ~1e5 times; a missed wake hangs the vCPU (the Phase 2 "missed
   wakes hang the guest" risk, now cross-thread where notify-before-wait
   is a real interleaving).
5. **Save/restore quiescence** — trigger save while vCPUs run; the
   coordinator must park all workers at a safe point; assert the image is
   internally consistent (no torn 64/128-bit values, mailbox records IDLE)
   and restores to a machine that still passes 1–4.
6. **TSO litmus tests** — small guest pairs pinned to two vCPUs, ~1e6 trials
   each, tallying outcome histograms:
   - *Message passing (MP)*: P0 `x=1; y=1`, P1 `r1=y; r2=x`. x86-TSO
     forbids `r1=1 ∧ r2=0`. Under option A ordinary MOVs compile to PLAIN
     wasm accesses (design doc Addendum 2), so a weakly-ordered host (ARM)
     MAY exhibit the forbidden outcome — this test is the detector that
     tells us whether the Phase 4 codegen needs release/acquire or fences on
     guest accesses, or can take QEMU MTTCG's calculated default risk (the
     Addendum 2 forward-risk note). Expected initially: violations observed
     on ARM hosts ⇒ a codegen decision, in files we own.
   - *Store buffering (SB)*: P0 `x=1; r1=y`, P1 `y=1; r2=x`. x86-TSO
     ALLOWS `r1=r2=0` (store buffers) — the harness must count, not flag,
     this outcome; it distinguishes "we need TSO" from "we accidentally
     require seq-cst", bounding how much fencing is even correct to add.
7. **Guest-level stress** — Alpine SMP fixture (the Phase 2 smp.js image):
   futex-heavy pthread workloads (producer/consumer, `pthread_mutex`
   ping-pong, `stress-ng --futex`), assert completion, no kernel soft-lockup
   splats, and exact application-level counters. The end-to-end sum over
   everything above.

## Layer A findings worth feeding back into the Phase 3/4 docs

- **Mailbox cost is real but fine for cold paths**: ~5.5–6.7 µs median
  round trip (Node/M4) ≈ 380–460 guest instructions at the 68 MIPS
  interpreter baseline — quantitative backing for §3's "hot paths avoid the
  mailbox entirely"; virtio/DMA must keep their direct views. p99 spikes to
  ~37 µs under scheduler noise, so Phase 4 should not put anything
  latency-critical (e.g. TSC reads) behind it.
- **`Atomics.waitAsync` re-arm pattern**: the load → service-or-waitAsync
  loop with a bounded timeout (mailbox-protocol.js / helpers.js
  `main_thread_wait_for`) survived 30k RPCs with zero lost wakeups; the
  stale-expected `"not-equal"` immediate return is what makes the re-arm
  race benign. Recommend this exact loop as the Phase 4 device-host
  skeleton — and always with a timeout so a protocol bug hangs loudly.
- **Signed returns from gram atomics**: wasm i32 results surface in JS as
  SIGNED; any Phase 4 JS-side caller comparing against values ≥ 2^31 must
  `>>> 0` (the JIT/Rust callers are unaffected). Worth one line in the gram
  ABI header comment.
- **Generator output is not concurrency-safe**: `fs.writeFileSync` is not
  atomic — a process reading `build/gram-shared.wasm` while another runs the
  generator can observe a truncated file (hit in development when workers
  raced to generate; fixed by generating on the main thread and shipping
  bytes via `workerData`). If anything ever invokes the generator outside
  make's serialization, it should write temp-then-rename.
- **CAS contention behaves**: ~0.9 retries per success at 4 workers on one
  cell — no livelock tendency in V8's rmw.cmpxchg on imported shared
  memory; Phase 4 spin-loop lowerings can rely on forward progress.
- **Race detectability on this host is strong** (42–65 % lost updates in
  every plain run), so Layer A exactness passes are meaningful — but the
  plain-race test intentionally reports INCONCLUSIVE instead of failing on
  a lucky run: keep that semantics when wiring into CI, and treat repeated
  INCONCLUSIVE on a CI host as "this host cannot validate Layer A", not as
  green.
